============================================================
RESUMO EXECUTIVO
============================================================

Stack:
React 18, TypeScript, Vite, Express 5, Socket.IO, WebRTC, Prisma 7, PostgreSQL, Redis, JWT, bcrypt e Nodemailer.

Arquitetura:
Monorepo com frontend e backend parcialmente integrados. O backend concentra rotas, autenticacao e regras de negocio em um unico arquivo, backend/src/index.ts. O estado de matchmaking e sessoes permanece em memoria.

Estado geral:
MVP funcional em partes, mas nao pronto para producao. Existem falhas de build, CI, autenticacao, autorizacao, persistencia, contratos de API e cobertura de testes.

Seguranca:
Ha vulnerabilidades confirmadas de autorizacao, exposicao de dados e configuracao insegura de JWT, CORS e cookies.

Performance:
Consultas sem indices adequados, historico JSON ilimitado, polling frequente e matchmaking com estruturas em memoria.

Qualidade do codigo:
152 problemas de lint, uso excessivo de any, funcoes extensas, tratamento de erros silencioso e logica duplicada.

Testes:
45 testes unitarios frontend passam quando isolados. O backend nao executa pelo script atual. O E2E e incluido indevidamente pelo Vitest e falha no carregamento.

Manutenibilidade:
Baixa a media. O sistema depende de URLs hardcoded, contratos nao centralizados e regras espalhadas entre frontend e backend.

DETALHES DOS PROBLEMAS MAIS IMPORTANTES
============================================================

[CRITICA] Mass assignment no perfil
Local: backend/src/index.ts:901-942

Evidencia:
const { cefrLevel, ...bodyData } = req.body;
const updateData = {
  ...bodyData,
  ...(cefrLevel ? { level: cefrLevel } : {})
};
await prisma.user.update({ where: { id: user.id }, data: updateData });

Qualquer usuario autenticado pode tentar enviar campos como reputation, isBanned, reportCount, email, password, flagStatus ou sessionsHistory.

Correcao:
Usar schema Zod com allowlist explicita somente para campos editaveis: name, level, bio, interests, birthDate, gender e pronouns. Nunca derivar diretamente o objeto Prisma do body da requisicao.

[CRITICA] Chat direto sem autorizacao
Local: backend/src/index.ts:724-767

O endpoint cria mensagens apenas com senderId autenticado e recipientId enviado pelo cliente. Nao verifica amizade, existencia do destinatario ou bloqueio.

O WebSocket possui o mesmo problema:
io.to(`user_${parsedData.recipientId}`).emit('direct_message', ...)

Impacto:
Qualquer usuario autenticado pode ler e enviar mensagens para qualquer outro usuario conhecido.

Correcao:
Centralizar uma funcao assertCanMessage(senderId, recipientId) e exigir relacao accepted nos endpoints HTTP e Socket.IO.

[CRITICA] Exposicao de hash de senha
Local: backend/src/index.ts:772-793

Evidencia:
return res.status(200).json({
  ...user,
  reputationScore: `${user.reputation ?? 100}/100`,
  feedbacks,
});

O spread inclui password, alem de todos os campos privados.

Correcao:
Sempre usar select explicito, nunca retornar o objeto Prisma completo.

[ALTA] JWT com segredo padrao
Local: backend/src/index.ts:35-36

Evidencia:
const JWT_SECRET = process.env.JWT_SECRET || 'seu-segredo-super-seguro';

Em producao, ausencia de configuracao transforma o segredo em valor publico e previsivel.

Correcao:
Falhar no startup se JWT_SECRET nao existir e exigir tamanho minimo.

[ALTA] IDOR em amizade
Local: backend/src/index.ts:574-648

Evidencia:
await prisma.friendRelation.updateMany({
  where: { id: String(requestId) },
  data: { status: 'accepted' }
});

O codigo nao garante que a relacao tenha friendId igual ao usuario autenticado. Basta conhecer o ID da relacao.

A remocao de amizade tambem aceita o ID da relacao diretamente em backend/src/index.ts:694-719.

Correcao:
Validar o proprietario da solicitacao:
where: { id: requestId, friendId: userId, status: 'pending' }

[ALTA] Bug no banimento permanente
Local: backend/src/index.ts:376-389

Evidencia:
if (newReportCount >= 3 && flagStatus === 'clean') {
  flagStatus = 'warning';
} else if (newReportCount >= 6 && flagStatus === 'warning') {
  flagStatus = 'suspended';
} else if (newReportCount >= 10) {
  flagStatus = 'banned';
}

Quando chega a 10 denuncias, flagStatus ja e suspended. Nenhuma condicao anterior transforma o status em banned.

Correcao:
Avaliar o numero primeiro:
if (newReportCount >= 10) flagStatus = 'banned';
else if (newReportCount >= 6) flagStatus = 'suspended';
else if (newReportCount >= 3) flagStatus = 'warning';

O incremento tambem deveria ser atomico ou realizado em transacao.

============================================================
ARQUITETURA ATUAL
============================================================

O frontend possui paginas grandes que fazem renderizacao, chamadas HTTP, controle de sessao, WebSocket e regras de negocio simultaneamente. O backend concentra praticamente todas as rotas em index.ts, incluindo autenticacao, amizade, mensagens, denuncias e perfil.

O Socket.IO possui autenticacao duplicada em backend/src/index.ts:148-162 e backend/src/sockets/matchmaking.ts:44-61.

Redis e configurado apenas como adapter do Socket.IO. As filas e sessoes continuam em Map local, portanto Redis nao resolve persistencia ou coordenacao do matchmaking.

A documentacao descreve endpoints e recursos inexistentes, como /api/match/find, /api/admin/*, /api/room/quality e /api/room/want-to-talk-again, conforme docs/ARCHITECTURE.md:70-115.

Problemas arquiteturais:
- Backend monolitico em um arquivo de quase mil linhas.
- Regras criticas sem camada de servico.
- DTOs e schemas nao centralizados.
- Estado de negocio em memoria.
- Contrato frontend/backend nao tipado nem gerado.
- Documentacao divergente da implementacao.
- Autenticacao HTTP e WebSocket duplicada.
- Historico de sessoes modelado como JSON em User.
- Ausencia de health check e graceful shutdown.
- Ausencia de camada de autorizacao reutilizavel.

Arquitetura recomendada:
1. Criar modulos auth, users, friends, messages, rooms e moderation.
2. Extrair schemas Zod e DTOs por dominio.
3. Criar servicos para autorizacao e regras de negocio.
4. Persistir sessoes, filas e preferencias no PostgreSQL/Redis.
5. Criar cliente frontend unico baseado em VITE_API_URL.
6. Compartilhar uma instancia Socket.IO por sessao autenticada.
7. Adicionar testes de integracao HTTP e WebSocket.
8. Gerar contratos compartilhados entre frontend e backend.

============================================================
BANCO DE DADOS
============================================================

Problemas encontrados:
- A migracao cria somente indice unico para email.
- Nao ha indices para FriendRelation.userId, FriendRelation.friendId e status.
- Nao ha indices para mensagens por remetente, destinatario e data.
- Nao ha indices para relatorios por usuario/status.
- Report nao possui relacoes Prisma com User.
- Campos status, flagStatus e level sao strings livres.
- sessionsHistory e minutesHistory sao arrays JSON sem limite.
- Atualizacoes de reputacao e historico podem perder dados em concorrencia.
- Relatorios duplicados nao sao controlados.
- reportCount usa leitura seguida de escrita, vulneravel a race condition.

Recomendacao:
Criar tabelas normalizadas para ConversationSession, Rating e SessionMetric, adicionar constraints/enums e usar transacoes atomicas.
